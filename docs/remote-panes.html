Remote Panes

How to expose a Cubicle manager over TLS, trust it from another machine, list remote workspaces, and understand the current state of remote pane attachment.

Works today TLS manager connections, remote registration, and cube ps -a listing.
Partly available Desk can target one manager endpoint, including a TLS endpoint.
Not complete yet Seamless local Desk panes attached to remote controllers still need a controller relay or remote controller listener.

Start A TLS Manager

On the remote host, start the manager with a TLS listener. The manager also keeps its local Unix socket available for local clients.

cubicle-manager daemon --listen tls://0.0.0.0:7443

Use a specific bind address if you only want to expose it on one interface:

cubicle-manager daemon --listen tls://192.0.2.10:7443

The TLS certificate and key are generated under the manager state directory when missing.

Authorize Your Client Key

On the client machine, print your Cubicle public key:

cube identity pub

On the remote host, add that public key to the workspace you want to access. Run this against the remote manager's local socket.

cube --workspace Project access add CLIENT_PUBLIC_KEY --role owner --label laptop

Use operator instead of owner when the client should run and attach to cubes but not manage workspace access keys.

Register The Remote

On the client machine, add the remote manager by name. The name is local to this client.

cube remote add lab tls://lab.example.com:7443

cube remote add connects to the remote manager, prints the manager public key, and asks whether to trust it. For non-interactive setup, use:

cube remote add lab tls://lab.example.com:7443 --yes

Inspect or remove the saved remote with:

cube remote list
cube remote inspect lab
cube remote remove lab

List Remote Workspaces And Cubes

After registration, cube ps -a includes remote workspaces. Remote workspace names are shown with the remote suffix.

cube ps -a

Example output shape:

Workspace Local
  shell       term      running

Workspace Project@lab
  build       term      running
  test        stream    completed

The @lab suffix means the workspace was discovered through the local remote named lab.

Use Desk With A Remote Manager

Desk currently connects to one manager endpoint for a session. To point Desk directly at a remote TLS manager, start it with CUBICLE_MANAGER_SOCKET set to that endpoint:

CUBICLE_MANAGER_SOCKET=tls://lab.example.com:7443 desk --workspace Project

You can also put the remote endpoint in client configuration as client.manager, then run desk --workspace Project.

Current attachment limitation

The remote registry is enough for discovery, and Desk can connect to a TLS manager when explicitly pointed at it. Seamless mixed local and remote panes in one Desk session are not complete yet.

Process attachment still depends on the controller endpoint returned by the manager. Today that endpoint is commonly a Unix socket path on the manager host, which a different machine cannot open. Full remote panes need either manager-relayed attachment streams or remotely reachable authenticated controller endpoints.

Troubleshooting

The remote does not connect

  • Verify the manager is listening with cubicle-manager daemon --listen tls://HOST:PORT.
  • Verify the port is reachable from the client host.
  • Use cube remote inspect NAME to confirm the saved endpoint.

The remote workspace is listed but attachment fails

This is expected with the current remote implementation when the controller endpoint is a remote Unix socket. Use the remote machine directly, or start Desk on the remote manager endpoint and keep this limitation in mind until controller relay support lands.

The local socket is missing after starting TLS

Recent builds keep the local Unix socket when the manager is started with --listen tls://.... Rebuild and restart the manager if an older daemon is still running.
