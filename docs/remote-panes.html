Remote Panes

How to expose a Cubicle manager over TLS, trust it from another machine, list remote workspaces, and attach to remote panes.

Works today TLS manager connections, remote registration, cube ps -a, and remote cube connect.
Desk desk --workspace name@remote opens a remote workspace through the saved remote.
Not complete yet One Desk session still targets one manager; mixed local and remote panes in the same Desk layout are future work.

Start A TLS Manager

On the remote host, start the manager with a TLS listener. The manager also keeps its local Unix socket available for local clients.

cubicle-manager daemon --listen tls://0.0.0.0:7443

Use a specific bind address if you only want to expose it on one interface:

cubicle-manager daemon --listen tls://192.0.2.10:7443

The TLS certificate and key are generated under the manager state directory when missing.

Authorize Your Client Key

On the client machine, print your Cubicle public key:

cube identity pub

On the remote host, add that public key to the manager. Run this against the remote manager's local socket; the grant applies to every workspace on that manager.

cube access add CLIENT_PUBLIC_KEY --role owner --label laptop

Use operator instead of owner when the client should run and attach to cubes but not manage workspace access keys.

Register The Remote

On the client machine, add the remote manager by name. The name is local to this client.

cube remote add lab tls://lab.example.com:7443

cube remote add connects to the remote manager, prints the manager public key, and asks whether to trust it. For non-interactive setup, use:

cube remote add lab tls://lab.example.com:7443 --yes

Inspect or remove the saved remote with:

cube remote list
cube remote inspect lab
cube remote remove lab

List Remote Workspaces And Cubes

After registration, cube ps -a includes remote workspaces. Remote workspace names are shown with the remote suffix.

cube ps -a

Example output shape:

Workspace Local
  shell       term      running

Workspace Project@lab
  build       term      running
  test        stream    completed

The @lab suffix means the workspace was discovered through the local remote named lab.

Connect To A Remote Cube

After the remote is registered, use the remote-qualified workspace name with cube connect:

cube --workspace Project@lab connect build

You can also put the workspace and cube in one selector:

cube connect Project@lab.build

cube connects to the remote manager over TLS and relays controller I/O through that manager connection, so the client does not need direct access to controller Unix sockets on the remote host.

Direct manager selection also works:

cube --manager-socket tls://lab.example.com:7443 --workspace Project connect build

Use Desk With A Remote Workspace

After the remote is registered, open a remote workspace by suffixing the workspace with the remote name:

desk --workspace Project@lab

Desk connects to the saved TLS manager for lab and relays pane attachment through that manager.

You can also point Desk directly at a remote TLS manager:

CUBICLE_MANAGER_SOCKET=tls://lab.example.com:7443 desk --workspace Project

You can also put the remote endpoint in client configuration as client.manager, then run desk --workspace Project.

Current Desk limitation

A Desk session currently targets one manager. desk --workspace Project@lab opens remote panes from lab, but the same Desk layout cannot yet mix local panes with panes from another remote.

Troubleshooting

The remote does not connect

  • Verify the manager is listening with cubicle-manager daemon --listen tls://HOST:PORT.
  • Verify the port is reachable from the client host.
  • Use cube remote inspect NAME to confirm the saved endpoint.

The remote workspace is listed but attachment fails

Make sure both client and manager are from a build that includes remote attachment relay support. Older managers return only remote Unix controller socket paths, which clients on another host cannot open.

The local socket is missing after starting TLS

Recent builds keep the local Unix socket when the manager is started with --listen tls://.... Rebuild and restart the manager if an older daemon is still running.
