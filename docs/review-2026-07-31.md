# Cubicle review findings — 2026-07-31

Reviewed current `main` at commit `13b9742df7304e906cfe6b54154f280f1c985445` (`Split controller into internal modules`).

This is a source-level review. The code was not compiled or executed in the review environment, and the latest commit had no attached GitHub CI status checks.

## Summary

The project has progressed well beyond its initial scaffold. It now contains a credible stream-mode prototype with:

- a manager/controller split,
- one thin controller per managed process,
- workspace and process registries,
- stream stdin/stdout/stderr mediation,
- persisted output with byte offsets,
- a local controller protocol,
- catch-up plus live attachments,
- primitive durable events,
- manager event aggregation,
- recovery cursors,
- unit and integration tests,
- optional lcov coverage support.

The core architecture remains sound. The most important work before adding TTY support is to harden controller lifecycle, isolate client failures, make control responses nonblocking, and provide transactional manager state.

## Findings

### 1. Critical — controller becomes unreachable when stdout and stderr close

`stream_event_loop()` runs only while its `open_count` is greater than zero. That count tracks the stdout and stderr pipes, not whether the child is still alive.

A child can legitimately close both output descriptors and continue running. When that happens, the event loop exits, the controller closes its control socket, and then blocks in `waitpid()`.

Consequences:

- `status`, `signal`, and `terminate` become unavailable;
- stdin attachments stop working;
- the controller can block indefinitely waiting for a still-running process.

The event loop should continue until both conditions are true:

1. the child has exited; and
2. all output pipes have reached EOF.

Recommended implementation:

- periodically call `waitpid(child_pid, &status, WNOHANG)` inside the event loop, or
- integrate `SIGCHLD` through a self-pipe or `signalfd` on Linux.

Add a regression test with a child that closes stdout and stderr, then waits for a signal.

### 2. Critical — partially initialized controller state is used on an error path

If `initialize_controller_state()` fails, `run_stream()` calls `wait_for_child(child_pid, &state)` and `close_controller_state(&state)`.

Some initialization failures may occur before all controller-state fields are valid. `wait_for_child()` may then try to append an event through an invalid `events_fd`.

Recommended changes:

- initialize the structure at declaration with all descriptors set to `-1`;
- track whether durable state is fully initialized;
- split child waiting from durable event recording;
- record the exit event only when the state journal is valid.

For example, separate:

- `wait_for_child_raw(pid, &status)`; and
- `record_child_exit(&state, status)`.

### 3. High — synchronous control responses can block or fail the whole controller

Accepted control sockets are nonblocking, but request handlers synchronously write responses and catch-up data using `cubicle_write_all()`.

Affected paths include:

- `read` responses,
- metadata responses,
- event responses,
- attachment catch-up output.

A client can request a large response and then stop reading. A synchronous response may hit `EAGAIN`, monopolize the controller, or turn one slow client into a controller-wide failure.

Recommended design:

- give every control client a bounded outbound queue;
- represent file-backed responses using cursor and remaining-length state;
- request `POLLOUT` only when a client has pending output;
- advance each client incrementally from the main poll loop;
- detach a client when its bounded queue remains full.

This should be implemented before TTY catch-up, where response volume and timing will be more demanding.

### 4. High — attachment failures are not consistently isolated to the attachment

The architecture intends to fail closed per attachment. However, errors from functions such as stdin forwarding or request handling can currently cause `stream_event_loop()` to return an error, taking down the controller path.

The failure boundary should be:

- malformed client request, disconnected client, client backpressure, or client write failure: close only that client;
- failure of a controller-owned process pipe, journal, listening socket, or core poll loop: fail the controller.

Add tests where:

- a stdin attachment disconnects while data is being forwarded;
- a client sends a malformed or oversized request;
- an output observer stops reading;
- other attachments and the managed process remain healthy.

### 5. High — manager persistence is not concurrency-safe

The manager currently acts as a command-line program that directly reads and appends TSV files.

Operations such as workspace creation perform separate steps:

1. check whether a name exists;
2. generate an ID;
3. append a record.

Two concurrent manager invocations can race and create duplicate workspace names or inconsistent process/cursor state.

This is important because Cubicle is explicitly designed for simultaneous terminals, UIs, scripts, and agents.

Recommended direction:

- make the manager a persistent daemon that serializes mutations;
- use SQLite for authoritative global state;
- enforce uniqueness and referential integrity in the schema.

Suggested constraints include:

```sql
UNIQUE(workspace_name)
UNIQUE(workspace_id, friendly_name)
UNIQUE(process_id)
```

Readable controller-local logs can remain append-only text files. The manager registry should be transactional.

### 6. Medium — explicit state-directory reuse silently destroys prior state

Controller state files are created with truncation, including:

- `events.log`,
- `stdout.log`,
- `stderr.log`,
- metadata.

If a state directory is accidentally reused, prior process history is silently erased. Reuse can also collide with a still-running controller.

Recommended behavior:

- create new controller directories exclusively;
- treat an existing generated process directory as an invariant violation;
- provide a separate explicit recovery/open-existing path;
- never truncate an existing process record during normal launch.

### 7. Medium — control socket replacement is too aggressive

`open_control_socket()` unconditionally unlinks the requested path before binding.

This can remove:

- a live controller socket;
- an unrelated filesystem entry at a caller-supplied path;
- evidence that a duplicate controller is already active.

Recommended sequence:

1. inspect the existing path with `lstat()`;
2. require it to be a socket;
3. attempt to connect to determine whether it is live;
4. remove it only when it is demonstrably stale;
5. ensure the parent state directory is private;
6. set explicit socket permissions.

### 8. Medium — completed controllers disappear immediately

After the managed process exits and its output is drained, the controller records the exit and terminates. Persisted files remain readable through the filesystem, but the controller protocol and socket disappear.

A short completed-state retention phase would better match the intended architecture and improve manager recovery.

Suggested lifecycle:

```text
RUNNING
  -> DRAINING
  -> COMPLETED
  -> EXIT
```

During `COMPLETED`, allow:

- `status`,
- `metadata`,
- `events`,
- `read stdout`,
- `read stderr`.

Reject input, signals, and new interactive control. Exit after manager acknowledgement or a retention timeout.

## Strengths

The following choices are working well and should be preserved:

- The manager understands process meaning, namespaces, and policy; the controller owns one process and its I/O.
- Controller identity remains internal while process identity is user-facing.
- Each managed process receives its own process group.
- Stream stdin, stdout, and stderr are independently mediated.
- Output byte offsets provide a good resumable cursor model.
- Controller-local event sequences support manager restart and replay.
- Catch-up followed by live streaming is the right attachment abstraction.
- Splitting controller code into control, state, stream, and I/O modules improves the fault boundary and testability.
- The test suite already covers common utilities, process helpers, manager parsing, controller workflows, attachments, stdin policy, daemon mode, recovery reads, and manager events.

## Recommended implementation order

Before TTY support:

1. Keep the controller responsive until both child exit and output EOF.
2. Make every client failure attachment-local.
3. Replace synchronous control responses with poll-driven outbound queues.
4. Add a completed-state retention phase.
5. Move authoritative manager state to a daemon-backed transactional store.
6. Harden state-directory and control-socket creation.
7. Add regression tests for every failure mode above.

TTY and hybrid PTY/captured-stderr support will be substantially easier to build once these lifecycle and transport invariants are established.
